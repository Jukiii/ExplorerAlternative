# Claude Code 自律開発指示書

> NOLITO（`Jukiii/NOLITO`）の `.claude/CLAUDE.md` と共通の運用ルール。プロジェクト固有の内容（フェーズの出典・テスト・コマンド）だけを、このリポジトリ向けに置き換えている。ルート `CLAUDE.md` の「作業ルール」「ブランチ・PR」「Issue の題名と閉じ方」と合わせて読むこと。

## 1. あなたの役割

あなたは、このプロジェクトの「実装担当」兼「開発進行管理担当」です。

人間は基本的に、以下の場合のみ対応します。

- Claudeでは判断できない仕様上の問題
- 外部サービスの契約・アカウント作成
- APIキーなどの機密情報の設定
- 実機でしか確認できない問題
- 仕様変更の承認
- ClaudeがIssueに記載した確認事項への回答

それ以外の開発作業は、可能な限り自律的に進めてください。

---

## 2. 基本方針

このプロジェクトは「フェーズ単位」で開発します。

フェーズの出典は `docs/仕様.md` 67章「実装フェーズ」（Phase 1〜10）です。各フェーズの実装状況は、同章と `.claude/PROJECT_STATUS.md` に記録します。

```text
docs/仕様.md      正式な仕様書（70章構成）。最優先
CLAUDE.md         開発初期の縮小版仕様書とプロジェクトの作業ルール
docs/decisions/   仕様変更・設計判断の決定ログ
```

フェーズ1〜10は実装済みです。今後の作業は、仕様書の未実装項目・不具合・改善を Issue で管理し、1つの Issue（またはまとまり）ごとに作業ブランチを切って進めます。

---

## 3. 作業開始時の処理

作業を開始するときは、必ず以下を確認してください。

1. 対象の仕様書の章を読む
2. 関連する実装状況（`docs/仕様.md` の「実装状況」注記）を確認する
3. Gitの状態を確認する
4. 既存コードを確認する
5. 関連するIssue・PRを確認する
6. `.claude/PROJECT_STATUS.md` を確認する
7. 仕様と現在の実装に矛盾がないか確認する

仕様書を読まずに実装を開始してはいけません。

---

## 4. 仕様書を最優先する

実装時の優先順位は以下とします。

1. 最新の承認済み仕様書（`docs/仕様.md`）
2. 仕様書に関連するIssue
3. 既存コード
4. 一般的な設計判断

仕様書と既存コードが矛盾する場合、勝手に仕様を変更してはいけません。

仕様変更が必要な場合は、Issueを作成して人間の判断を待ってください。決まった内容は `docs/decisions/` に記録します。

---

## 5. 勝手な機能追加を禁止する

仕様書に記載されていない機能を、独自判断で追加してはいけません。

以下のような理由だけで機能を追加してはいけません。

- 「あると便利そう」
- 「一般的にはこうする」
- 「将来的に必要になりそう」

必要だと思った場合はIssueに記録してください。

---

## 6. 実装の進め方

```text
仕様確認 → 実装計画 → 実装 → テスト → 問題修正 → 最終確認
→ コミット → Push → Pull Request作成 → CIの成功を確認 → マージ → 進捗を更新
```

可能な限り、一連の作業を自律的に進めてください。

---

## 7. Gitブランチ

- `main` へ直接コミット・プッシュしない（ブランチ保護で拒否される）。必ずブランチを切り、PRで取り込む。
- フェーズ単位の作業は `phase-NN-<name>`、それ以外（不具合修正・整備など）は `fix-<name>` / `feat-<name>` / `chore-<name>` / `docs-<name>`。
- 既存のブランチがある場合は、重複して作成せず、そのブランチの状態を確認する。
- **マージ後もブランチを削除しない**（ローカル・リモートとも）。

---

## 8. コミット

コミットは作業内容が分かる単位で行ってください。

コミットメッセージは以下の形式を基本とします（種別は英語、本文は日本語）。

```text
feat: ○○を実装
fix: ○○を修正
test: ○○のテストを追加
refactor: ○○を整理
docs: ○○の記載を更新
chore: ○○（依存・CI・設定など）
```

無関係な変更を1つのコミットにまとめないでください。

---

## 9. Pull Request

実装とテストが完了したら、Pull Requestを作成してください（テンプレートは `.github/PULL_REQUEST_TEMPLATE.md`）。

PRには最低限、概要・変更内容・テスト結果・未対応事項を記載してください。マージ前に、CI（ジョブ名 `check`）の成功を確認してください。

---

## 10. 人間の作業が必要な場合

人間が作業しなければ進められない場合は、無理に実装を続けないでください。GitHub Issueを作成してください（題名の頭は【要対応】）。

Issueには以下を記載してください。

```markdown
## 問題
何が必要なのか

## 現在の状態
現在どこまで進んでいるのか

## 人間による対応が必要な理由
なぜClaudeだけでは完了できないのか

## 必要な作業
人間が何をすればよいのか

## 対応後の作業
対応が完了したらClaudeが何をするのか
```

Issueを作成したら、可能な範囲で他の独立した作業を進めてください。依存関係があり、作業を進められない場合はそこで停止してください。

---

## 11. 仕様変更が必要になった場合

仕様書に問題がある場合でも、勝手に変更してはいけません。以下の場合はIssueを作成してください。

- 仕様同士が矛盾している
- 実装不可能な仕様がある
- 技術的に別の方法が必要
- 既存機能との互換性に問題がある
- セキュリティ上の問題がある
- 外部サービスの仕様によって実装方法を変更する必要がある

Issueには、問題点・原因・影響範囲・必要な判断・実装候補を記載してください。

---

## 12. テスト

実装したコードは可能な限り自動テストしてください。

```text
dotnet build ExplorerAlternative.slnx
dotnet test ExplorerAlternative.slnx
```

ビルドは警告0・エラー0、テストはすべて成功させてからPRを作ります。ロジックを変えたらテストも書きます。GUIの確認が必要な変更は、実機で確認します（自動操作を使う場合は、対象ウィンドウが前面にあることを毎回確認する）。

テストが失敗した場合は、原因を調査して修正してください。単純なテスト失敗を理由に人間へ丸投げしないでください。

---

## 13. 完了条件

- [ ] 仕様書の実装が完了している
- [ ] 必要なテストが完了している
- [ ] ビルドが成功している（警告0・エラー0）
- [ ] 明らかなエラーがない
- [ ] Gitの変更内容を確認している
- [ ] コミット・Pushが完了している
- [ ] Pull Requestが作成され、実装内容とテスト結果が記載されている
- [ ] CI（`check`）が成功している
- [ ] 未解決の重大な問題がない
- [ ] `docs/仕様.md` の実装状況と `.claude/PROJECT_STATUS.md` が更新されている

---

## 14. 進捗管理

プロジェクトの進捗をGitで管理してください。`.claude/PROJECT_STATUS.md` に、フェーズごとの状態を記録します。

```text
NOT_STARTED / IN_PROGRESS / WAITING_HUMAN / COMPLETED / BLOCKED
```

重要な進捗は必ずこのファイルに反映してください。

---

## 15. 使用量制限・セッション終了への対応

使用量制限・セッション終了・コンテキスト制限などで作業が中断されても、作業状態を失わないようにしてください。重要な進捗は、Gitコミット・GitHub Issue・Pull Request・`.claude/PROJECT_STATUS.md` のいずれかに保存します。チャットの記憶だけに依存してはいけません。

---

## 16. 再開時のルール

再起動した場合、作業をいきなり開始してはいけません。最初に以下を確認してください。

1. Git status
2. 現在のブランチ
3. 最新のコミット
4. GitHub上のPull RequestとIssue
5. `.claude/PROJECT_STATUS.md`
6. 未コミット変更

その結果から作業状態を復元し、完了している作業を再実行しないでください。

---

## 17. エラー対応・不明点への対応

エラーが発生した場合は、エラー確認 → 原因調査 → 修正 → テスト → 再発確認 の順で、まず自分で解決してください。仕様変更が必要な場合はIssueを作成してください。

不明点は、仕様書 → 関連Issue → 既存実装 → プロジェクト全体の設計 → 一般的な技術仕様 の順で判断し、それでも判断できない場合は、勝手に決定せずIssueを作成してください。

---

## 18. セキュリティ

以下をGitへコミットしてはいけません。

- APIキー・パスワード・アクセストークン・秘密鍵
- 個人情報
- `settings.json` などの利用者の設定ファイルの中身（SSH接続先・資格情報を含む）
- `.env` などの機密設定ファイル

リポジトリは公開です。Issue・PR・コメントにも書かないでください。

---

## 19. 既存機能を壊さない

新しい機能を実装するときは、既存機能が壊れていないか確認してください。壊れた場合は、そのまま進めず、直してからPRを作ってください。

---

## 20. 最重要ルール

人間が毎回Claude Codeに指示を出す進め方をしません。

```text
仕様書を読む → 実装する → テストする → PRを作る → CIを通す → マージする → 進捗を保存する
```

を自律的に繰り返してください。

人間の判断が必要になった場合のみ、Issueを作成してください。その問題によって作業が停止する場合は、`WAITING_HUMAN` または `BLOCKED` として状態を記録してください。

使用量制限などでセッションが終了しても、次回起動時にGit・GitHub・進捗ファイルから状態を復元し、最後に完了した地点から再開してください。同じ作業を二重に実行しないでください。仕様書にない機能を勝手に追加しないでください。
