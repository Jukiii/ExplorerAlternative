# Windows向け高機能ファイルエクスプローラー 開発仕様書 v3

## AI開発プロンプト

あなたは経験豊富なWindowsデスクトップアプリ開発者です。
以下の仕様を満たす、実用レベルのWindows向け高機能ファイルエクスプローラーを設計・実装してください。

このアプリは **Windows 11 Explorer + 開発者向けターミナル/Git/SVN + macOS FinderのQuick Look + VS Code的な分割/ターミナル操作** を融合したファイルマネージャーを目指します。

## 1. 技術スタック

- C#
- .NET 10
- WPF
- Windows 11向けEXE
- MVVM等
- Git CLI
- SVN CLI
- OpenSSH / 必要に応じてSSH.NET
- Windows Credential Manager等の安全な認証保存

UIとロジックを分離し、拡張可能な構造にすること。

（実装状況・2026-09更新）ターミナル（9・17章）はWindows ConPTYではなく、標準入出力
リダイレクト方式（`PowerShellTerminalService`）で実装している。ConPTY化を試みたが
`STATUS_DLL_INIT_FAILED`により断念した経緯は17章参照。

## 2. UIデザイン

外観は **Windows 11のエクスプローラーを最優先**。

- Fluent Design
- Windows 11風ツールバー
- Windows 11風アイコン
- Windows 11風の余白
- 角丸
- ホバー
- Light / Dark / System
- 高DPI対応

VS Code風・macOS風の外観にはしない。
ただし、機能面ではVS CodeやFinderの便利な機能を取り入れる。

（実装状況・2026-09更新）アプリアイコンを設定した（`Assets/app.ico`、16〜256pxの
複数解像度を含む）。フォルダをモチーフに、メイン表示モードの階層表示（4.2章）で
使う展開記号「>」を白抜きで配置したデザイン。実行ファイル（タスクバー・タスク
トレイ含む）とウィンドウタイトルバーの両方に反映される。

（実装状況・2026-09更新）ユーザーからの明示的な指示により、配色をClaude.ai風の
暖色系（オレンジ系アクセント・クリーム色の背景）に変更し、あわせて角丸を全体的
に拡大した（ボタン・トグルボタン・ナビ項目・タブ・スクロールバーつまみ等）。本章
本文の「Windows 11のエクスプローラーを最優先」はレイアウト・操作感の指針として
維持しつつ、配色のみユーザー指示を優先する（31章「重要な判断ルール」参照）。
`Themes/LightTheme.xaml`・`Themes/DarkTheme.xaml`の`DynamicResource`ブラシキー
（`WindowBackgroundBrush`等）を差し替えるだけで全画面に反映される構造は変更して
いない。ターミナル・Diff・VCSバナー等、意味を持つ配色（緑=追加、赤=削除等）は
維持している。設定画面（63章）の`TabControl`は、Application.Resourcesでの
カスタムテンプレートがタブ本体の背景に反映されない環境だったため、各タブの中身
（Grid）に直接`WindowBackgroundBrush`を指定する方式で統一感を確保した。

（実装状況・2026-09更新）配色に続けて、ユーザー指示（「余白・間隔の調整」
「ツールバー/アドレスバーの見た目を刷新」「ナビペイン項目をカード風に」）に
従いレイアウトも一部刷新した。ペイン構成・列配置（3章の画面構成図）自体は
変更していない。
- ツールバー：戻る/進む/上へボタンの間隔を拡大し、余白を全体的に広げた。
- アドレスバー・表示モード切替・隠しファイル切替の背景を角丸10のピル形状に統一。
- パンくずドロップダウン（11章）のポップアップとホバー行にも角丸を適用した。
- ナビゲーションペイン（4章・6章）の各項目（お気に入り／タグ／ドライブ／
  ワークスペース／最近使った場所／最近のプロジェクト）を、ペイン背景から
  浮いて見える枠線付きの「カード」形状にし、項目間の余白も広げた
  （`NavListBoxItemStyle`、App.xaml）。

（実装状況・2026-09更新）上記カード化で各項目が縦に大きくなりすぎたため、
ユーザー指示により1項目あたりの高さを縮小した（`NavListBoxItemStyle`の
Padding・Marginを再調整）。カードの枠線・角丸自体は維持している。

## 4. 左ペイン

お気に入り・ナビゲーション用。

標準項目：

- 各ドライブ
- 最近使った場所
- お気に入り（Home/Desktop/Downloads/Documents/Pictures/Music/Videosを初期値として含む）
- タグ
- ワークスペース

ユーザーは任意のフォルダを追加可能。

- 追加
- 削除
- 並び替え
- ドラッグ＆ドロップ
- 右クリックメニュー

左ペインは表示/非表示、幅変更に対応し状態を保存する。

（実装状況・2026-09更新）当初はクイックアクセス（Home/Desktop等の固定一覧）と
お気に入りを別セクションとして表示していたが、ユーザー指示により統合。初回起動時
（お気に入りが空の場合）のみHome/Desktop/Downloads/Documents/Pictures/Music/Videos
をお気に入りの初期値として登録し、以降は他のお気に入りと同様に追加・削除・
名前変更・並び替え（▲▼ボタンおよびお気に入り欄内でのドラッグ&ドロップ）ができる
単一の一覧として扱う。ピン留めファイル（51章）はユーザー指示により削除した。

（実装状況・2026-09更新）GridSplitterで左ペイン・右のGit/SVN情報ペインの幅を
変更しても表示内容の幅が追従しない不具合を修正した（Border側に固定Widthを
指定していたため、列（枠）は広がっても中身の表示幅が変わらなかった。Borderの
指定をMinWidthに変更し、列幅にHorizontalAlignment=Stretchで追従するようにした。
折りたたみ時に列が縮む挙動は維持している）。

（実装状況・2026-09更新）上記MinWidthは60pxまで縮小し、それより狭く
GridSplitterで縮めた場合は水平スクロールバー（ScrollViewer）で中身を
確認できるようにした。また、GridSplitterはドラッグ後もキーボードフォーカスを
持ち続け、直後に矢印キーを押すと（ファイル一覧の移動のつもりでも）列幅が
変わってしまう問題があったため、GridSplitterをFocusable="False"にして
キーボードフォーカスを受け取らないようにした（マウスドラッグでの
リサイズ自体には影響しない）。

（実装状況・2026-09更新）ユーザー指示により、左ペインの項目の表示順を
お気に入り→タグ→ドライブ→ワークスペース→最近使った場所→最近のプロジェクト
に変更した。

（実装状況・2026-09更新）トラックパッドの横スワイプ（`WM_MOUSEHWHEEL`）による
水平スクロールに対応した。WPFのScrollViewerは既定でこれをハンドリングしない
ため、ウィンドウメッセージを直接フックし、カーソル直下のScrollViewerへ手動で
反映する方式にした（左右ペイン・ファイル一覧・Git/SVN情報ペインなど、
ScrollViewerを持つ箇所すべてに適用される）。

（実装状況・2026-09更新）上記の実装には、カーソル直下から祖先方向へ最初に
見つかったScrollViewerをそのまま使ってしまうという不具合があった。ナビペイン
内の各ListBoxが持つ内部ScrollViewer（既定では横スクロール無効）に当たってしまい、
ペイン全体を横スクロールしたいケースで実際には何も起きていなかった。横方向に
実際にスクロール可能な最も内側のScrollViewerを優先して探すように修正した
（`FindScrollViewerAt`、MainWindow.xaml.cs）。

（実装状況・2026-09更新）「最近使った場所」等、MaxHeightで内部スクロールが
必要な一覧で、ホイール操作しても一覧内をスクロールできない不具合を修正した。
原因は、ナビペイン内のListBoxのホイールイベントを常に外側のペイン全体の
ScrollViewerへ転送していたため（4章の「內側のListBoxが自身でスクロールを
消費してしまう問題」への対処が、逆に内部スクロールが必要な一覧の妨げに
なっていた）。内側のScrollViewerがその方向へまだスクロールできる間は
内側に処理させ、端に達している場合のみ外側へ転送するように修正した
（`NavListBox_PreviewMouseWheel`、MainWindow.xaml.cs）。

（実装状況・2026-09更新）トラックパッドの横スワイプが、MainWindow以外の
ウィンドウ（Log/フォルダ比較/SFTPブラウザ・Diff等）では一切効かない不具合を
修正した。`WM_MOUSEHWHEEL`のフックがMainWindowのHWNDにしか登録されておらず、
別ウィンドウ（別HWND）にはメッセージが届かないため何も起きていなかった。
フック処理を`TrackpadScrollSupport`（アプリ直下）へ切り出し、`Window`型の
`Loaded`イベントをクラスハンドラで一括購読することで、以降に開かれる
全てのWindow（MainWindow含む）へ自動的に適用されるようにした
（タイトルバーの明暗をDWM経由で全Windowへ適用する仕組みと同じ方式）。

（実装状況・2026-09更新）ユーザー指示により、横スクロールが存在する箇所全てで、
トラックパッドの横スワイプに加えて、通常ホイール＋Shift（Windows/Office等で
一般的な「Shiftを押しながらホイール＝横スクロール」の慣習）にも対応した。
`TrackpadScrollSupport`が`WM_MOUSEHWHEEL`（トラックパッド）と`WM_MOUSEWHEEL`
（Shift押下時のみ横スクロールとして扱う）の両方をフックする。個別の
Window/ScrollViewerで独自に実装する必要はなく、アプリ内のどのWindow・
ScrollViewer（ナビ/VCSペイン、Log、フォルダ比較、Diff、Quick Look画像
プレビュー等）でも自動的に両方の操作に対応する。新しく追加するWindowでも
`TrackpadScrollSupport.RegisterForAllWindows()`（App.xaml.cs起動時に1回登録
済み）により自動的に有効になるため、追加対応は不要。

バッジ部分（テキストのみの表示のため）には反映していない。

## 6. メイン表示モード

**通常の単純リスト表示は用意しない。**

切り替え可能なモード：

### 6.1 階層表示（主要モード）

```text
▾ 📁 Project
  ▾ 📁 src
    ▸ 📁 components
      📄 Button.cs
      📄 Header.cs
    📄 main.cs
  ▸ 📁 assets
  ▸ 📁 tests
  📄 README.md
```

- ファイルとフォルダを同じツリーに表示
- `▸` / `▾` を使用
- `+` / `-` は使用しない
- Lazy Loading
- UI Virtualization
- 非同期列挙
- フォルダに入らなくても下位階層を展開できる

（実装状況・2026-09更新）フォルダの展開・折りたたみ時は、表示リスト全体を
作り直すのではなく、開閉に伴い増減した項目だけを挿入・削除するようにした
（不具合修正：以前は展開・折りたたみのたびに表示リストをClear→再構築して
いたため、選択位置とスクロール位置が先頭に戻ってしまっていた）。

### 6.2 詳細表示

Windows 11 Explorer風。

```text
名前              更新日時             種類          サイズ
────────────────────────────────────────────────────
📁 Project         2026/09/01 22:10     フォルダー
📄 main.cs         2026/09/01 21:32     C#ファイル      12 KB
📄 README.md       2026/08/31 18:20     Markdown         4 KB
```

列候補：

- 名前
- 更新日時
- 作成日時
- 種類
- サイズ
- Git状態
- SVN状態
- タグ

列の表示/非表示、幅、順序を保存する。

（実装状況・2026-09更新）名前・サイズ・更新日時・種類・タグの列を実装。当初は
「種類」の代わりに「Git状態」の列を表示していたが、Git状態はファイル一覧の
バッジ表示（21章）で既に確認できるため、ユーザー指示により「種類」列に差し替えた
（拡張子ベースの簡易表示、例：「CSV ファイル」。フォルダは「ファイル フォルダー」）。
列ヘッダーの右クリックには何も割り当てていない（列の表示/非表示切替等は将来検討）。

（実装状況・2026-09更新）名前・サイズ・更新日時・種類の各列ヘッダーをクリックすると、
その列を基準に並び替えるようにした。同じ列を再度クリックすると昇順/降順が反転する。
フォルダは並び替え条件に関わらず常に先頭にまとまる。現在の並び替え列のヘッダーには
▲（昇順）/▼（降順）を表示する。タグ列はクリックしても並び替えは行わない。

## 7. 階層キーボード操作

- `↑ / ↓` 項目移動
- `→` フォルダ展開
- `←` フォルダ折りたたみ（展開中でない項目の場合は親フォルダを選択）
- `Alt + ↑` 親階層へ
- `Enter` 開く
- `F2` 名前変更
- `Delete` 削除
- `Space` Quick Look

（実装状況・2026-09更新）`←`は、選択中の項目が展開中のフォルダであればそれを
折りたたむ。それ以外（ファイル、または折りたたみ済みのフォルダを選択中）の
場合は、Windows標準のツリー操作に合わせて親フォルダを選択する（もう一度
`←`を押すと、選択された親フォルダが展開中であれば折りたたまれる）。

## 8. メイン領域の分割ビュー

**メイン表示領域だけ**を分割する。
左ペイン、ツールバー、ターミナル等は分割しない。

```text
┌────────────────────┬────────────────────┐
│ C:\Project         │ D:\Backup          │
│                    │                    │
│ ▾ 📁 src           │ ▾ 📁 src           │
│   📄 main.cs       │   📄 main.cs       │
│   📄 test.cs       │   📄 test.cs       │
└────────────────────┴────────────────────┘
```

機能：

- 縦分割
- 横分割
- 分割解除
- 左右/上下入れ替え
- ペインサイズ変更
- ペイン間フォーカス移動
- 複数ペイン
- ペインごとに独立した現在パス
- ペインごとに独立した表示モード

推奨：

- `Ctrl + \` 縦分割
- `Ctrl + Shift + \` 分割解除

ショートカットは設定から変更可能。

（実装状況・2026-09更新）`Ctrl + \`（右に分割）・`Ctrl + Shift + \`（ペインを
閉じる＝分割解除）のショートカットを実装した（メニュー・コマンドパレットからは
既に実行可能だったが、キーボードショートカットが未実装だった）。左右/上下入れ替え
は「ペインを入れ替え」（メニュー・コマンドパレット。`TabViewModel.SwapPanes`）
として実装済み（アクティブペインは入れ替え後も同じペインを指し続ける）。
ペインサイズ変更（GridSplitter等によるドラッグリサイズ）は未実装で、分割ペインは
`UniformGrid`による等分割のみ（今後の課題）。

## 9. アクティブペイン

分割ビューでは必ずアクティブペインを持つ。

ファイル・フォルダ・余白をクリックしたペインをアクティブにする。

### 視覚的表示

アクティブペインは **背景を明確に強調**。

単なる細い枠線だけにせず、背景色・透明度・選択状態等を使い、現在操作対象のペインが一目で分かるようにする。

Light / Dark両方で十分な視認性を確保。

アクティブペインに以下を適用：

- アドレスバー
- 検索
- Git / SVN
- ファイル操作
- Quick Look
- キーボード操作
- Terminal Sync
- コピー/移動
- 新規作成
- 表示モード

（実装状況・2026-09更新）当初はアクティブペインを青枠＋青背景（強度は設定の
「アクティブペイン背景強調度」で調整）で強調していたが、ユーザー指示により
方式を変更。現在はアクティブ側を着色するのではなく、非アクティブ側のペインに
黒の半透明オーバーレイ（同じ強調度設定を流用）をかけて少し薄暗くすることで、
相対的にアクティブペインを目立たせている。

## 10. タブ

- `Ctrl + T` 新規タブ
- `Ctrl + W` タブを閉じる
- `Ctrl + Tab` タブ切替
- タブ固定
- スマートタブ
- 同一フォルダの重複タブを抑制可能

タブごとに可能な限り以下を保持：

- 現在パス
- 履歴
- 表示モード
- 展開状態
- ペイン構成
- ターミナル状態

### Ctrlドラッグによるタブ複製

タブを `Ctrl` を押しながらドラッグすると、そのタブを複製する。

複製時には可能な限り以下を引き継ぐ：

- 現在パス
- 履歴
- 表示モード
- 展開状態
- ペイン構成
- ターミナル状態

## 17. PowerShellターミナル

画面下部に統合ターミナル。

Windows ConPTYを利用（想定）。ただし下記（実装状況）の通り、実機での互換性問題
によりシェルプロセス側は標準入出力リダイレクト方式で実装し、画面側の構造のみ
VS Codeの統合ターミナルに合わせている。

- 複数タブ
- 追加/削除
- コピー/ペースト
- ANSIカラー
- スクロール
- Ctrl+C等
- リサイズ
- PowerShellプロファイル

`Ctrl + @` で表示/非表示。

高さはドラッグ変更可能。

（実装状況・2026-09更新）VS Codeの統合ターミナルと同じ構造へ作り直した。
VS Codeは「ターミナル画面（xterm.js）＋シェルプロセス（node-pty→ConPTY）」の
2層構造だが、本アプリはConPTY（後述の調査参照）が使えないため、シェルプロセス側は
標準入出力リダイレクト方式のままとし、画面側の構造をVS Codeに合わせている。

- **単一のターミナル画面**：出力欄と入力欄を分けず、1つの`RichTextBox`
  （`TerminalSurface`）で扱う。プロンプト（`PS C:\...>`）はシェル自身が出力した
  ものであり、その末尾に直接入力する。旧実装が別の入力欄を持っていたのは、
  標準出力を「行単位」で読んでいたため改行で終わらないプロンプトが表示できなかった
  ことによる。生の文字ストリームとして読むよう変更して解消した。
- **入力の扱い**：PowerShellは受け取ったコマンドをエコーバックするため、確定時に
  ローカルの入力文字を画面から消してから送信し、二重表示を防いでいる。入力行の
  編集（文字入力・Backspace・Delete・←→・Home/End・貼り付け）とコマンド履歴
  （↑↓）はコードビハインドで実装している。なおスペースキーはWPFの読み取り専用
  エディターがKeyDown段階で消費してTextInputが発生しないため、明示的に処理している。
- **ANSIカラー**：`AnsiTextParser`がSGRシーケンス（16色・256色・フルカラー・
  太字・反転）を解釈して色付きで描画する。Windows PowerShell 5.1自身はリダイレクト時に
  ANSIを出力しないが、git・npm等の外部ツールの出力はそのまま通過するため有効に働く
  （`TERM`/`FORCE_COLOR`/`CLICOLOR_FORCE`環境変数を設定して色出力を促している）。
  SGR以外のCSI（カーソル移動・画面消去）とOSCは読み飛ばす。単独のCRによる行上書き
  （プログレスバー）は未対応で、行が積み上がる。
- **文字コード**：PowerShell 5.1は自身のメッセージをOEMコードページ（日本語環境は
  CP932）で、gitなどの開発ツールはUTF-8で出力するため、1本の標準出力に2種類の
  文字コードが混在する。`TerminalOutputDecoder`がチャンクごとに「正しいUTF-8として
  解釈できるか」を判定して切り替えることで、両方を文字化けなく表示する。標準入力側は
  PowerShellが期待するOEMコードページで書き込む（日本語ファイル名のドラッグ&ドロップ対策）。
- **高さのドラッグ変更**：パネル上端のつまみ（`Thumb`）で変更できる（80〜900px）。
- **Ctrl+C（実行中コマンドの中断）**：選択範囲があればコピー、なければ本物の
  Ctrl+Cシグナルを送る。本アプリはコンソールを持たないGUIプロセスだが、
  `CreateNoWindow`で起動した子シェルは（ウィンドウが無いだけで）コンソールを持つため、
  一時的にそのコンソールへ`AttachConsole`し、`GenerateConsoleCtrlEvent`で
  `CTRL_C_EVENT`を発生させる方式を採った。イベントはそのコンソールに紐づく全プロセス
  （アタッチ中の自プロセスを含む）へ配送されるため、送信前に`SetConsoleCtrlHandler(NULL, TRUE)`で
  自プロセスのCtrl+C処理を無効化し、アプリ自体が終了しないようにしている。アタッチは
  プロセス全体の状態を変えるため、全ターミナルで直列化し、UIを止めないようバックグラウンドで
  実行する。アタッチに失敗した場合はETX(0x03)送信にフォールバックする。
  実機検証では`ping -n 40`が5回で中断され、PowerShellが`Ctrl+C`と表示して新しい
  プロンプトへ戻り、シェル・アプリとも生存したままであることを確認済み。
  コピー/ペーストはCtrl+C（選択時）/Ctrl+Vで可能。
- 複数タブ・タブの追加/削除・スクロール・PowerShellプロファイル読込（設定でON/OFF）・
  `Ctrl + @`表示切替・Explorerとの現在フォルダ同期は引き続き実装済み。

（2026-09調査）ConPTY化を試みたが、`CreatePseudoConsole`/`CreateProcess`等の
Win32 API呼び出しはすべて成功を返すにもかかわらず、疑似コンソール経由で
起動した子プロセス（`cmd.exe`・`powershell.exe`のいずれでも再現）が起動直後
（100ms以内）に`STATUS_DLL_INIT_FAILED`（0xC0000142）で異常終了する現象が、
開発環境・ユーザーの実機の両方で再現した。Microsoft公式サンプルと同一の実装
（構造体レイアウト・`UpdateProcThreadAttribute`の`lpValue`がHPCONへの
ポインタである点を含む）で検証済みのため、実装バグの可能性は低いと判断し、
標準入出力リダイレクト方式へ戻した。

調査で切り分けた事実：
- ユーザーの実機ではWindows Terminal（ConPTYを内部利用）・VS Codeの統合
  ターミナル（node-pty経由でConPTYを内部利用）はいずれも正常に動作しており、
  OS自体がConPTYに完全非対応というわけではない。
- `STARTUPINFOEX`の拡張属性リスト機構自体（属性0件で`EXTENDED_STARTUPINFO_PRESENT`
  のみ指定）は正常に動作し、失敗するのは疑似コンソール属性
  （`PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`）を設定した場合のみ。
- `CREATE_NO_WINDOW`・`bInheritHandles`（true/false）・OS互換性マニフェストの
  有無・.NETのCoreCLRホストか`Add-Type`経由のPowerShellホストか、いずれの
  組み合わせでも同一の失敗が再現。
- Windows Terminalアプリの再インストール、`sfc /scannow`（整合性違反なし）、
  `DISM /RestoreHealth`（正常完了）、再起動、いずれでも解消せず。
- 実機にはConPTYの同梱ホスト`C:\Windows\System32\OpenConsole.exe`が存在せず、
  Windows TerminalのStoreパッケージ内のコピーに依存している（一般的な構成
  ではない可能性がある）。
- Process Monitorでの実機キャプチャにより、失敗の瞬間に`conhost.exe`が
  名前付きパイプの読み取りで`PIPE BROKEN`を検出していること、また
  `CreateProcess`を呼び出した側のプロセス自身が`conhost.exe`を直接
  開こうとする形跡（本来ConPTY使用時は発生しないはずの挙動）を確認した。
  `HKCU\Console\%%Startup`の`DelegationConsole`/`DelegationTerminal`を
  明示的に従来のWindowsコンソール（`{B23D10C0-E52E-411E-9D5B-C09FDF709C7D}`）
  に固定しても解消しなかった。

以上より、このマシン固有のOS内部の状態（コンポーネントのバージョン不整合等、
未特定）に起因する可能性が高いと判断し、これ以上の深掘り（WinDbgでの
カーネルレベルのデバッグが必要）は行わず、標準入出力リダイレクト方式を
維持する方針とした。再挑戦する場合は、上記の切り分け結果を出発点にすること。

`PatchService`のプロセス起動箇所すべてでUTF-8を明示するよう修正し、Status
表示・Diff・Patchも含めて解消した。

（実装状況・2026-09更新）フォルダ移動のたびに、Git/SVNのステータス取得

## 62. ファイル操作安全性

大量操作・削除・上書き等は対象と内容を明示。

危険操作は確認ダイアログを出す。

（実装状況・2026-09更新）67章Phase 7「操作履歴・GUI Undo」を実装した。移動・
コピー・名前変更・複製・新規作成（フォルダ/ファイル）・ショートカット作成・
一括リネームを対象に、アプリ全体で1つの操作履歴（スタック、最大50件）を共有し、
`Ctrl+Z`または「☰ メニュー」→「元に戻す」（次にUndoされる操作の内容をラベルに
表示）で直近の操作を1件ずつ元に戻せる。実行主体は`IUndoService`で、各操作の
完了直後に巻き戻し処理（例：移動なら元の親フォルダへ戻す）を記録する。Undo後の
表示更新は、対象フォルダを監視している`FileSystemWatcher`ベースの自動更新
（20章・64章）に任せており、Undo自体が個別に画面を再構築するわけではない。

以下は明示的にUndo対象外とする。
- **削除（ごみ箱送り）**：Windowsのごみ箱から特定の項目だけを復元するには、
  ごみ箱の内部形式を扱うCOM相互運用（`IFileOperation`等）が必要で、本実装の
  対象外とした。ごみ箱から手動で復元するか、Windowsエクスプローラー自体の
  Undoを利用する。
- **競合時の「上書きする」**（Ctrl+ドラッグで同名の項目が既に存在する場合）：
  上書きされた元の内容をバックアップしていないため、元に戻すと内容が失われる。
  「名前を変更してコピー」を選べばUndo対象になる。

Redo（やり直し）は対象外（今後の拡張候補）。

UIスレッドで重い処理を実行しない。

（実装状況）検索・巨大ファイル検索・重複ファイル検索（ハッシュ計算含む）・
空フォルダ検索はバックグラウンド処理＋キャンセル可能（`IFolderScanService`、
`CancellationToken`）。テキストプレビューは`StreamReader.ReadBlock`で
先頭の必要な文字数のみを読み込み、ファイル全体をメモリに載せない。
`FileSystemWatcher`（`IFolderWatcherService`）により、他アプリ・ターミナル・
Git操作等による外部からのファイル変更を検知し、短時間の連続変化は
デバウンス（400ms）してから自動的に一覧を更新する（タブ/ペインを閉じる際に
監視も解放する）。UI Virtualizationは標準のListBox/ListViewの既定動作に
依拠している。

（実装状況・2026-09更新）同じフォルダの再読み込み（F5・上記の外部変更検知）に
限り、再読み込み前の選択状態・展開状態をフルパスで記録しておき、再構築後に
同じパスのノードへ復元するようにした（別フォルダへの移動時は対象外）。

不具合修正：この復元処理は当初、展開済みフォルダ1件ごとに表示リスト全体を
Clear→再構築してしまっており、展開済みフォルダの数が多い場合（例：30個の
フォルダを展開した状態でF5）に再構築が連鎖してアプリがフリーズしたように
見える不具合があった。展開状態の復元中は表示リストの再構築を抑制し、復元
完了後に1回だけ再構築するよう修正した。

## 65. セキュリティ

- SSH秘密情報を平文保存しない
- 外部コマンド引数を適切に扱う
- Git / SVN / PowerShell実行の安全性を考慮
- 不要な管理者権限を要求しない
- 危険操作には確認
- リモート操作も誤操作防止
- 任意EXE起動時の引数を適切にエスケープ

（実装状況）SSHパスワードはWindows Credential Manager経由で保存（44章）。
外部ツール実行（22章）は、対象パスに空白が含まれ、かつ引数テンプレート側で
未引用の場合に自動的に二重引用符で囲むよう修正済み（修正前は空白を含む
パスを渡すと引数が分割されてしまう不具合があった）。レジストリ操作
（Explorer連携・システムトレイ関連）・グローバルホットキー登録は
いずれもHKEY_CURRENT_USER配下／管理者権限不要なAPIのみを使用している。
削除は既定でごみ箱経由、破棄的なGit操作（Discard/Reset等）は確認ダイアログを
経由する。
